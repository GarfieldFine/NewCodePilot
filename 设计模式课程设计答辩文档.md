# CodePilot 后端设计模式应用 — 课程设计答辩文档

## 一、项目简介

**CodePilot** 是一个 AI 驱动的代码审查平台，基于 **Spring Boot 3 + WebFlux + MyBatis Plus + Project Reactor** 构建。系统通过多 Agent 流水线自动分析 GitHub Pull Request，结合规则引擎与多 AI 模型，生成风险评估报告并实时推送给前端。

**技术栈**：Java 17、Spring Boot 3.x、Spring WebFlux、MyBatis Plus、Redis、Project Reactor、Lombok、Hutool

> 本文档用于设计模式课程设计答辩，按 **GoF 23 种设计模式** 的分类体系，逐一说明每种模式在本项目中的实际应用。

## 二、创建型模式

### 2.1 单例模式（Singleton）

**Spring 容器管理的所有 Bean 默认都是单例**，这是本项目应用最广泛的模式——每个 `@Component`、`@Service`、`@RestController`、`@Configuration` 标注的类在容器中只存在一个实例。

```java
// 所有以下组件在 Spring 容器中均为单例
@Component  public class ReviewEngine { ... }
@Service   public class PrAnalysisService { ... }
@RestController public class PrAnalysisController { ... }
@Configuration public class RedisConfig { ... }
@Component  public class AiProviderFactory { ... }
```

**为什么用单例**：这些组件是无状态的（依赖注入的 Bean 由 Spring 管理），复用同一实例避免了反复创建对象的开销，也保证了全局配置一致性。

### 2.2 工厂模式（Factory Method / Abstract Factory）

本项目有多处显式的工厂类，利用 **Spring 集合注入** 自动收集所有接口实现，再按名称或策略匹配返回具体实例。

#### AiProviderFactory — AI 模型工厂

```java
@Component
public class AiProviderFactory {
    private final Map<String, AiProvider> providers;  // Spring 自动注入所有 AiProvider 实现
    private final String defaultProvider;

    public AiProviderFactory(List<AiProvider> providerList,
                             @Value("${ai.default-provider}") String defaultProvider) {
        this.providers = providerList.stream()
                .collect(Collectors.toMap(AiProvider::getProviderName, p -> p));
        this.defaultProvider = defaultProvider;
    }

    public AiProvider getProvider(String name) {
        // 按名称查找，未配置则回退到默认 provider
        AiProvider provider = providers.get(name.toLowerCase());
        if (provider == null) provider = providers.get(defaultProvider);
        return provider;
    }
}
```

**核心思想**：客户端只需传入 provider 名称（如 `"deepseek"`），工厂负责查找并返回对应实例，解耦了客户端与具体 AI 模型的创建逻辑。

#### ReviewStrategyFactory — 审查策略工厂

```java
@Component
public class ReviewStrategyFactory {
    private final List<ReviewStrategy> strategies;  // Spring 自动注入所有 ReviewStrategy 实现

    public ReviewStrategyFactory(List<ReviewStrategy> strategies) {
        this.strategies = new ArrayList<>(strategies);
        this.strategies.sort(Comparator.comparingInt(ReviewStrategy::getPriority));
    }

    public ReviewStrategy findStrategy(String language, List<String> frameworks) {
        return strategies.stream()
                .filter(s -> s.supports(language, frameworks))
                .findFirst()
                .orElse(defaultStrategy);  // 找不到匹配策略时使用默认策略
    }
}
```

**核心思想**：根据 PR 中检测到的编程语言和框架，自动选择最合适的审查策略，实现了"由子类决定实例化哪个类"。

#### SemanticAnalyzerFactory — 语义分析器工厂

同理，`SemanticAnalyzerFactory` 管理所有 `CodeSemanticAnalyzer` 实现，按语言支持程度和优先级分派文件到对应的语义分析器。

#### Spring 自身的 Factory Method

```java
@Configuration
public class WebClientConfig {
    @Bean  // 每个 @Bean 方法都是一个工厂方法
    public WebClient webClient() {
        return WebClient.builder()
                .codecs(config -> config.defaultCodecs().maxInMemorySize(10 * 1024 * 1024))
                .build();
    }
}
```

### 2.3 建造者模式（Builder）

本项目通过 **Lombok @Builder** 注解，在 **20+ 个数据类** 上应用了建造者模式。这使得复杂对象的构建过程链式调用，代码清晰易读。

**典型示例**：

```java
// AgentEvent.java — Agent 事件对象
@Builder
public class AgentEvent {
    private String traceId, agentName, message;
    private AgentEventType type;
    private Map<String, Object> metadata;
}
```

**实际构建代码**（来自 `ReviewEngine.java:306`）：

```java
return AnalysisResult.builder()
```

### 2.4 原型模式（Prototype）

`AgentContext.cloneForProvider()` 实现了深拷贝，为多模型并行分析场景隔离状态。

```java
// AgentContext.java
public AgentContext cloneForProvider(String providerName) {
    AgentContext clone = new AgentContext();
    clone.analysisId = this.analysisId;
    clone.prInfo = this.prInfo;              // 共享只读数据
    clone.repositoryContext = this.repositoryContext;
    clone.ruleResults = this.ruleResults;
    clone.providerName = providerName;       // 重设 provider
    clone.chunkReviews = new ArrayList<>();  // 重置 provider 特异性数据
    clone.aiReviewResult = null;
    return clone;
}
```

**应用场景**：多 AI 模型并行审查时，共享阶段 1-2（仓库分析、风险检测）的结果，然后 clone 出 N 份上下文分发给各 Provider 并行执行阶段 3-4，避免数据污染。

### 3.4 组合模式（Composite）

#### PersonaPromptBuilder — Prompt 组装

```java
@Component
public class PersonaPromptBuilder {
    private final List<ReviewerPersona> personas;  // Spring 注入所有 Persona 实现

    public String buildSystemPrompt(String language, List<String> frameworks) {
        StringBuilder prompt = new StringBuilder(promptManager.getBasePrompt());
        // 组合最多 3 个活跃 Persona 的 prompt 扩展
        personas.stream()
                .filter(ReviewerPersona::isActive)
                .limit(3)
                .forEach(p -> prompt.append(p.getPromptExtension()));
        // 组合语言策略的 prompt 扩展
        ReviewStrategy strategy = strategyFactory.findStrategy(language, frameworks);
        prompt.append(strategy.getSystemPromptExtension());
        return prompt.toString();
    }
}
```

**核心思想**：将多个 Persona 和 Strategy 视为同一接口的"组件"，组合它们各自贡献的 prompt 片段，最终合并为一个完整 prompt。单个组件和组合后的整体对外暴露相同的调用方式。

## 四、行为型模式

### 4.1 策略模式（Strategy）

#### 审查策略 — 按语言定制审查重点

**策略接口**：

```java
public interface ReviewStrategy {
    String getName();
    boolean supports(String language, List<String> frameworks);
    List<String> getFocusAreas();          // 该语言的审查关注点
    String getSystemPromptExtension();     // 注入 AI 的领域知识
    default int getPriority() { return 100; }
}
```

**6 个具体策略**：

| 策略类 | 优先级 | 适用语言/框架 |
|--------|--------|--------------|
| `JavaReviewStrategy` | 10 | Java, Kotlin, Spring, MyBatis, Maven, JPA |
| `FrontendReviewStrategy` | 15 | TypeScript, JavaScript, React, Vue, Next.js |
| `PythonReviewStrategy` | 20 | Python, Django, Flask, FastAPI |
| `GoReviewStrategy` | 30 | Go, Gin, Echo |
| `SqlReviewStrategy` | — | SQL |
| `DefaultReviewStrategy` | 1000 | 所有语言（兜底） |

**具体策略示例**：

```java
@Component
public class JavaReviewStrategy implements ReviewStrategy {
    @Override
    public List<String> getFocusAreas() {
        return List.of(
            "Concurrency Safety (thread pools, synchronized, volatile, locks, atomic)",
            "Transaction Management (@Transactional scope, isolation levels, propagation)",
            "Spring Context (bean scopes, circular dependencies, lifecycle hooks)",
            "SQL/ORM (N+1 queries, indexing, batch operations, lazy loading)",

            "Exception Handling (exception propagation, logging, error codes)",
            "Memory Management (object allocation, GC pressure, memory leaks)",
            "API Design (REST conventions, versioning, backward compatibility)"
        );
    }

    @Override

        return """

    }
}
```

### 4.2 模板方法模式（Template Method）

#### AbstractAiProvider — AI 调用的骨架

```java
public abstract class AbstractAiProvider implements AiProvider {

    // 模板方法 — 定义算法骨架（final 语义，通过不暴露覆盖点实现）
    @Override
    public String chat(String systemPrompt, String userPrompt) {
        String requestBody = buildRequestBody(systemPrompt, userPrompt);  // 父类实现
        String response = webClient.post()
                .uri(getApiUrl())            // → 子类提供
                .headers(h -> getHeaders().forEach(h::add))  // → 子类提供
                .bodyValue(requestBody)
                .retrieve()
                .bodyToMono(String.class)
                .block(Duration.ofSeconds(120));
        return extractContent(response);     // 父类实现
    }

    // 钩子方法 — 子类必须实现
    protected abstract String getApiUrl();
    protected abstract String getApiKey();
    protected abstract String getModel();
    protected abstract Map<String, String> getHeaders();
}
```

**5 个子类仅需覆写钩子方法**：

```java
// DeepSeekProvider — 与 OpenAI 兼容的 API
@Component("deepseek")
public class DeepSeekProvider extends AbstractAiProvider {
    @Override protected String getApiUrl() { return "https://api.deepseek.com/v1/chat/completions"; }
    @Override protected String getApiKey() { return apiKey; }
    @Override protected String getModel() { return model; }
}
```

**ClaudeProvider 为什么没有继承 AbstractAiProvider？**

因为 Anthropic 的 API 格式与 OpenAI 完全不同（`system` 是顶层字段而非 message、响应使用 `content[0].text` 而非 `choices[0].message.content`），强行复用模板会导致过多 if-else，违反开闭原则。因此 ClaudeProvider 直接实现 `AiProvider` 接口，独立实现全部逻辑。这体现了"不为了模式而模式"的设计原则。

#### Agent 接口 — 具有默认方法的模板

```java
public interface Agent {
    AgentResult execute(AgentContext context);  // 子类必须实现

    // 模板方法 — 提供默认实现的骨架
    default Mono<AgentResult> executeAsync(AgentContext context) {
        return Mono.fromCallable(() -> execute(context))
                .subscribeOn(Schedulers.boundedElastic());
    }

    default void executeStreaming(AgentContext context, Consumer<AgentEvent> eventSink) {
        execute(context);  // 默认退化到同步执行
    }

    default boolean shouldRun(AgentContext context) { return true; }
    default int priority() { return 100; }
}
```

### 4.3 观察者模式（Observer）

本项目使用 **Project Reactor 的 SSE（Server-Sent Events）** 实现了一套类观察者的事件推送系统。

**事件体系**：

```java
// 事件类型枚举
public enum AgentEventType {
    AGENT_STARTED, AGENT_RUNNING, AGENT_COMPLETED, AGENT_FAILED,
    AGENT_SKIPPED, PIPELINE_STAGE, CHUNK_PROGRESS, AI_TOKEN,
    ANALYSIS_COMPLETE, ERROR, MULTI_PROVIDER_COMPLETE
}

// 事件对象（@Builder）
public class AgentEvent {
    private String traceId, agentName, message;
    private AgentEventType type;
    private Map<String, Object> metadata;
}
```

**被观察者（Subject）** — `AgentExecutor` + `AgentPipeline` 在执行过程中持续发射事件：

```java
// AgentPipeline — 流水线每进入一个阶段就发射事件
eventSink.accept(AgentEvent.pipelineStage(context.getAnalysisId(), stage.name()));

// AgentExecutor — Agent 启动/完成/失败时发射事件
eventSink.accept(AgentEvent.started(context.getAnalysisId(), agent.getName()));
eventSink.accept(AgentEvent.completed(context.getAnalysisId(), agent.getName()));
```

**观察者（Observer）** — 前端通过 SSE 订阅事件流：

```java
@RestController
public class PrAnalysisController {
    @GetMapping(value = "/api/v1/pr/analyze/stream", produces = "text/event-stream")
    public Flux<ServerSentEvent<AgentEvent>> analyzeStream(...) {
        return prAnalysisService.analyzeStream(request)
                .map(event -> ServerSentEvent.<AgentEvent>builder()
                        .id(event.getTraceId())
                        .event(event.getType().name())
                        .data(event)
                        .build());
    }
}
```

**SSE 中转站** — `SseEmitterService` 以 `ConcurrentHashMap<String, Sinks.Many<String>>` 管理每个分析任务的事件通道，实现多分析任务的事件隔离。

**对比传统观察者**：传统观察者通常在同一 JVM 内同步通知，而本项目的观察者（浏览器）通过网络接收事件，是**跨进程的异步观察者**，利用了 Reactor 的背压机制防止生产过快。

### 4.4 责任链模式（Chain of Responsibility）

#### AgentPipeline — 多阶段审查流水线

```java
// ReviewEngine.buildStages() — 定义链结构
private List<PipelineStage> buildStages() {
    return List.of(
        new PipelineStage("Understanding Repository",
                List.of(repositoryAnalyzeAgent, diffAnalyzeAgent, contextBuildAgent),
                ExecutionMode.SEQUENTIAL),       // 阶段 1: 顺序执行三个 Agent
        new PipelineStage("Detecting Risks",
                List.of(riskDetectAgent),
                ExecutionMode.SEQUENTIAL),       // 阶段 2: 单一 Agent
        new PipelineStage("Generating AI Review",
                List.of(reviewGenerateAgent),
                ExecutionMode.SEQUENTIAL),       // 阶段 3: AI 审查
        new PipelineStage("Merging Analysis",
                List.of(summaryMergeAgent),
                ExecutionMode.SEQUENTIAL)        // 阶段 4: 合并结果
    );
}

// AgentPipeline — 链式执行
public AgentContext execute(List<PipelineStage> stages, AgentContext context, ...) {
    for (PipelineStage stage : stages) {
        if (stage.mode() == PARALLEL)
            results = agentExecutor.runParallel(stage.agents(), context, eventSink);
        else
            results = agentExecutor.runSequential(stage.agents(), context, eventSink);
    }
    return context;
}
```

**数据传递**：`AgentContext` 在链中传递，每个 Agent 读写 `AgentContext`，后一个阶段消费前一阶段的产出。

**多模型并行变体**：阶段 1-2 共享执行一次 → 克隆 N 份上下文 → 阶段 3-4 在每个 Provider 上并行执行 → 合并结果。

#### RuleEngine — 规则链

```java
@Component
public class RuleEngine {
    private final List<Rule> rules;  // Spring 注入所有 10 条规则

    public List<RuleResult> analyze(PrInfo prInfo) {
        List<RuleResult> results = new ArrayList<>();
        for (PrFile file : prInfo.getFiles()) {
            for (Rule rule : rules) {
                if (rule.isEnabled()) {
                    RuleResult result = rule.evaluate(file, prInfo.getDiff());
                    results.add(result);
                }
            }
        }
        return results;
    }
}
```

每条 `Rule` 独立判断是否匹配，无需 AI 参与，与传统 AI 审查并行互补。

MyBatis Plus 的 `BaseMapper<T>` 提供了标准 CRUD 方法，无需手写 SQL：

```java

    // 继承自 BaseMapper: insert, updateById, selectById, selectList, deleteById ...
    
    @Select("SELECT * FROM analysis_records WHERE pr_url = #{prUrl} ORDER BY created_at DESC")
    AnalysisRecord findByPrUrl(String prUrl);  // 自定义查询

```

## 七、设计亮点与答辩要点

### 7.1 模式组合运用

1. **策略 + 工厂 + 模板方法**：`ReviewStrategy`（策略）由 `ReviewStrategyFactory`（工厂）创建，`PersonaPromptBuilder`（组合）将它们组装进最终的 AI Prompt
2. **责任链 + 观察者**：`AgentPipeline`（责任链）逐阶段推进，每个阶段通过 `Consumer<AgentEvent>`（观察者回调）向 `SseEmitterService` 发射事件，前端通过 SSE 实时接收
3. **原型 + 责任链**：多模型并行场景下，`AgentContext.cloneForProvider()`（原型）创建 N 份副本，每份走独立的审查链

### 7.2 不盲目套用模式

- **ClaudeProvider 不继承 AbstractAiProvider**：因为 Anthropic API 与 OpenAI 格式差异太大，强行复用模板会导致大量条件分支，违反开闭原则
- **没有 Command 模式**：虽然有多 Agent，但共享 `AgentContext`，用责任链比 Command 更自然
- **没有 Visitor 模式**：语义分析器是直接调用，不需要双重分派

### 7.3 关键数字

| 指标 | 数值 |
|------|------|
| GoF 模式覆盖 | **14 种**（创建型 4 + 结构型 4 + 行为型 5 + 架构级 4） |
| 策略实现数 | 6 个（覆盖 Java、Python、Go、前端、SQL、通用） |
| AI Provider 数 | 5 个（Claude、OpenAI、DeepSeek、Qwen、SiliconFlow） |
| Agent 数 | 6 个（仓库分析、Diff 分析、上下文构建、风险检测、审查生成、结果合并） |
| 责任链阶段 | 4 阶段（理解仓库 → 检测风险 → AI 审查 → 合并分析） |
| 规则引擎规则数 | 10 条 |
| @Builder 应用类数 | 20+ |

## 八、总结

本项目在 AI 代码审查这一业务场景中，**自然地应用了 14 种设计模式**，覆盖了 GoF 23 种模式中的大部分重要模式。模式的选择遵循"为变化而设计"的原则：

- **AI 模型的多样性** → 工厂 + 模板方法
- **编程语言的差异性** → 策略 + 组合
- **审查流程的阶段性** → 责任链 + 外观
- **审查过程的实时性** → 观察者（SSE）
- **多模型的并行性** → 原型 + 责任链
- **数据来源的异构性** → 适配器
- **复杂对象的构建** → 建造者

所有模式均为业务需求驱动，无过度设计，体现了设计模式在实际工程中的正确应用方式。
